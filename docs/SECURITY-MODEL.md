# Security model

What an attacker might try, and what stops them. "Bridge" is the verifier sidecar ([BRIDGE-API.md](BRIDGE-API.md)).

| # | Threat | Mitigation | Where |
|---|---|---|---|
| 1 | **Cross-device QR relay.** The attacker opens the login page, sends the QR code to a victim (phishing page, chat), and the victim's wallet logs the attacker's browser in. | No cross-device flow fully prevents this. OpenID4VP 1.0 §14.2 admits its Response Code defence does not work across devices, and RFC 10027 (BCP 247) lists the mitigations used here: short-lived single-use requests (TTL 60–600 s, default 180), rate limits, and a request signed by the verifier's certified identity (`x509_san_dns:` client id), so the wallet can show who is asking. **Prefer same-device login through the Digital Credentials API**, which binds the request to the page's origin: with `BRIDGE_DC_API_ORIGINS` set, a browser that has the API asks the wallet itself, the wallet binds its presentation to the page's origin, and the verifier checks that binding, so a relayed request cannot log another page in. The QR code remains the fallback. | Bridge (`dc_api`), `login.js`, `InitiateController` |
| 2 | Guessing or stealing an attempt id to poll or complete someone else's login. | 128-bit `public_id` plus a 256-bit secret in an HttpOnly, SameSite=Strict cookie whose hash the attempt stores. The cookie is `__Host-` and `Secure` whenever the site's home URL is HTTPS, even behind a TLS proxy that hides HTTPS from PHP. Unknown and foreign attempts both answer 404. | `BrowserBinding`, `BrowserController::bound_attempt()` |
| 3 | Cross-site requests to the login endpoints. | SameSite=Strict cookie plus a login-page token. The token is the same for every visitor (what WordPress computes for a logged-out user), so it is a cross-site check only, not a binding; unlike a regular nonce it also works for a logged-in visitor on wp-login.php. | `PageToken`, `BrowserController::check_page_request()` |
| 4 | Forged webhook delivery. | Shared secret header (≥ 32 characters, constant-time compare) and optional IP allowlist on the direct peer address. The body is never trusted: the event is always re-read from FireFly by id (no setting turns this off), and a 404 is ignored. FireFly cannot sign webhooks (v1.5), which is why the re-read matters. | `WebhookController`, `AttestationProcessor` |
| 5 | Replayed webhook or poll applying an attestation twice; double click on complete. | Compare-and-set status transitions (`UPDATE … WHERE status = ?`); `consumed` is terminal. | `AttemptRepository::transition()` |
| 6 | A forged `LoginAttested` event from another contract. | The decoder checks both the configured listener and `attestor_address` against the actual emitting address. The contract permits one decision per correlation ID, emitted only by an owner-authorised verifier. | `ContractEventDecoder`, `SsiLoginAttestor` |
| 7 | A compromised or buggy bridge answering WordPress with a different subject than it attested. | WordPress recomputes `sha256(correlation_id ":" blinding_secret ":" subject_id)` and compares the presentation hash with the on-chain values. A mismatch refuses the login and fires `bloclabs_ssi_commitment_mismatch`. The same check runs before a token is issued to an agent. | `LoginChecks::verified()`, shared by `LoginFinalizer` and `TokenIssuer` |
| 8 | Tracking people by reading the chain, or testing a guessed subject id (an organisation's `did:web`, a DID from a registry) against the attestations. | Only commitments go on chain. The subject commitment is blinded with a random per-attempt secret that WordPress and the bridge hold and that never reaches the chain or the browser, so a reader of the chain can neither link one holder's logins nor confirm a guess. The `correlation_id` is public (an event topic) and salts nothing on its own. The browser sees neither value. | Contract, `Attempt`, `Attestation`, bridge |
| 9 | Account takeover through claim matching ("this credential says ada@example.com"). | Not offered. Subjects log in only to accounts they were linked to, or (opt-in) get a new account. | `UserResolver` |
| 10 | Self-registration into a powerful role. | Provisioning never grants a role that can `manage_options`, `edit_users` or `promote_users`; it falls back to subscriber. | `UserResolver::safe_role()` |
| 11 | Table and verifier flooding by anonymous `/initiate` calls: from one address, from addresses rotated inside an IPv6 prefix, from many addresses, or with a forged forwarded-for header. | Per-client cap on attempts opened in 10 minutes (default 10) and a site-wide cap behind it (default 500), both counting failed and expired attempts too. A client is an IPv4 address or an IPv6 /64, keyed by an HMAC; a request without a usable client address is refused. The caps are checked before the row is inserted and again by the row's rank among the window's rows, so a parallel burst cannot overshoot. Behind a proxy, set `client_ip_header` only if the origin is reachable through that proxy alone, and `client_ip_proxies` to the number of proxies that append to it: the client is taken that many entries from the right, never from the left, where the sender writes. Leave `client_ip_header` empty when the web server already resolves the client (Apache `mod_remoteip`, which the official WordPress Docker image turns on, or nginx `real_ip`): it sets `REMOTE_ADDR` to the client and removes the entries it consumed from the header, so the header PHP sees holds only what the sender wrote, and a visitor who sends one picks the address the cap counts. The settings page warns when the configured header is missing from the administrator's own request, the trace such a server leaves. Hourly purge; rows deleted after a day. `POST /agent/initiate` is counted in the same window under the same caps (A14). | `InitiateController`, `PurgeExpired`, `ClientIp` |
| 12 | Open redirect after login. | `redirect_to` is validated with `wp_validate_redirect()` at initiate and again after the `login_redirect` filter. | `InitiateController`, `CompleteController` |
| 13 | Malicious wallet URL from a compromised bridge (`javascript:`). | Only `openid4vp://` and `https://` are accepted, server side and again in the browser; values are set with `textContent` and `href`, never HTML. | `PresentationOffer`, `login.js` |
| 14 | Secrets leaking through the database or settings screen. | Secrets can be pinned in `wp-config.php` (`BLOCLABS_SSI_*`), are never printed back, and are excluded from REST. | `Settings`, `SettingsPage` |
| 15 | Exposing FireFly. | FireFly core has no authentication. Keep it on a private network; the plugin supports an `Authorization` header for an authenticating proxy. | Deployment |
| 16 | Bypassing other login protections (spam flags, lockouts, bans). | Before the cookie is set, the user goes through what a password login gets: the `wp_authenticate` action, the `wp_authenticate_user` filter (applied by the plugin itself, since core's password callbacks return early for a `WP_User` and never reach it) and the `authenticate` filter (multisite spam check and whatever plugins hook there), then `bloclabs_ssi_allow_login`, which must return exactly `true`. A `WP_Error` or a different user from any of them refuses. `wp_login` fires afterwards, as `wp_signon()` does. Two-factor plugins that work by intercepting `wp_login` on wp-login.php should veto through `bloclabs_ssi_allow_login` instead. An agent token goes through the same checks when it is issued, and `wp_authenticate_user` and `authenticate` again on every request it authenticates, so a lockout or a spam flag cuts an agent off at once. | `LoginChecks::check_user()`, shared by `LoginFinalizer` and `TokenIssuer`; `BearerAuthentication` |
| 17 | A verified login lost to a slow or failing verifier. | `/complete` checks everything before it consumes the attempt; a transient verifier error leaves the attempt `verified` and the browser retries. Only a definitive refusal (commitment mismatch, unlinked credential, veto) fails it. `POST /agent/token` answers 503 in the same case and the agent retries. | `LoginFinalizer`, `TokenIssuer`, `login.js`, agent client |
| 18 | A log dropped by a chain reorganisation logging someone in. | Configure evmconnect `confirmations.required > 0` on chains subject to reorganisation, sized for the chain's finality risk. evmconnect does not set `Removed`; checkpoints and `protocol_id` deduplication prevent a later removal notice for an applied event. WordPress cannot roll back a verified attempt or an issued session. Ignoring a hypothetical `removed: true` event is defensive parsing, not reorg protection. QBFT relies on its finality assumptions. | evmconnect configuration / chain finality |
| 19 | Reading claims from the bridge's result route. | WordPress refuses to start a login unless the bridge Authorization header is set, and the bridge must require it. The result route belongs on the private network; the wallet-facing host serves only OpenID4VP endpoints. | `InitiateController`, BRIDGE-API.md |
| 20 | A deleted account's credential left pointing at nothing. | Links are removed on `deleted_user` and on removal from a site; a link to a missing user counts as no link. | `Plugin`, `UserResolver` |
| 21 | A site administrator on multisite pointing the plugin at a bridge and FireFly they run, or turning on account creation, to mint accounts across the network or make WordPress call URLs of their choosing. | On multisite the settings page and its save require `manage_network_options` (through `option_page_capability_bloclabs-ssi-login`), so only network administrators change where WordPress sends requests and which accounts it creates. Keys pinned in `wp-config.php` are out of reach of the form altogether. | `SettingsPage` |
| 22 | A credential from an issuer the site never trusted: an attacker's own issuer with a valid signature, or a trusted issuer presenting a credential type it is not trusted for. | Issuer trust is a `(issuer, vct)` pair in the on-chain `TrustedIssuerRegistry`, unknown pairs untrusted ([ADR 0006](adr/0006-trusted-issuer-registry.md)). With `FIREFLY_REGISTRY_API` set, the bridge queries `isTrusted` through FireFly for the signature-checked credential's own issuer and `vct` before it attests; `false`, or a credential that names no issuer or no `vct`, is attested as a rejection, and no usable answer (FireFly unreachable, the API missing, an output that is not a boolean) means no attestation at all (fail closed). The query is a read, so the issuer and type of a login are not written to the chain. Without the setting, trust is the walt.id `allowed-issuer` policy in the bridge configuration, as in 0.2. | Bridge, `TrustedIssuerRegistry` |
| 23 | Widening the trust list quietly: a compromised registry owner key, a compromised bridge, or an operator adding a rogue issuer. | Only the registry owner can call `setIssuer`, through a two-step ownership transfer; the owner key is held away from the bridge, whose signing key can attest but not change the list, and WordPress holds no chain key. Every change is an `IssuerSet` event with the caller's address, so the chain carries the list's whole history and a FireFly listener on it can alert. A compromised owner key is detectable, not preventable, by the chain: its custody is the mitigation. | `TrustedIssuerRegistry`, deployment |

## Agent login (ADR 0007)

An agent logs in with the same credential flow and gets an opaque application token instead of a cookie
([ADR 0007](adr/0007-agent-login.md)). The threats below are the ADR's, numbered A1–A14 as there, with where each
mitigation lives now that it is built. "Agent client" is the reference client in [`demo/agent/`](../demo/agent/).

| # | Threat | Mitigation | Where |
|---|---|---|---|
| A1 | A stolen token (an agent's logs, environment or memory). | The token is opaque (`bssi_` and 256 random bits), accepted as an `Authorization: Bearer` header on `/wp-json/` requests only, over HTTPS unless `wp_get_environment_type()` is `local` (the rule core applies to Application Passwords; `bloclabs_ssi_agent_token_requires_https` overrides), never in a query string, a cookie, wp-admin, `wp-login.php`, `admin-ajax.php` or XML-RPC. Its scope cannot reach the account's own settings (A4). It lives `agent_token_ttl` seconds (300–86400, default 3600), never past the credential's expiry. It is stored as its SHA-256, so a database dump holds no usable token. The principal, an administrator or the agent (`DELETE /agent/token`) can revoke it, effective on the next request; `last_used_at` shows on the principal's list. | `AgentToken`, `IssuedToken`, `BearerAuthentication`, `ScopeEnforcement`, `ProfileScreen` |
| A2 | Prompt injection: an attacker opens an agent attempt and feeds its `wallet_url` to the victim's agent, which presents the credential; the attacker, holding the attempt secret, gets the token. The agent-side form of threat 1. | No protocol prevents it, as none does for people. The reference client presents only to the wallet URL its own `POST /agent/initiate` returned (it has no other input for one), and checks who is asking before it discloses anything: the request's `client_id` must be the one the wallet URL named and, if pinned with `--verifier`, the pinned one; a `redirect_uri:` id must name the `response_uri`; an `x509_san_dns:` or `x509_hash:` id needs a signed request whose certificate carries that name or hash. The token is scoped and short-lived, every token is on the principal's list, and every presentation the agent made is on the chain. | Agent client (`flow.mjs`, `oid4vp.mjs`), bridge (signed requests), `ProfileScreen` |
| A3 | A trusted issuer, or a compromised one, delegates any linked account to any agent through `acts_for`. | The registry pins `(issuer, vct)` for the agent credential type, so a site should run its own agent-credential issuer (threat 22). Delegation needs the principal's opt-in, *Agents may act for this account*, off by default. Every delegated token is listed and revocable on the principal's profile, and turning the opt-in off revokes them all. The login filters still run for the principal. | `TrustedIssuerRegistry`, `UserResolver::resolve_agent()`, `AgentDelegation`, `LoginChecks`, `ProfileScreen` |
| A4 | Scope escalation: using the token to change the principal's password or e-mail, mint an Application Password, or reach capabilities the scope does not list, including through a multisite super administrator, whom `has_cap()` grants everything unless `map_meta_cap` says `do_not_allow`. | `map_meta_cap` answers `do_not_allow` for every primitive capability outside the scope, for everything on the denylist, and for the account's self-service meta capabilities (`edit_user`, `delete_user`, `promote_user`, the Application Password ones); that binds super administrators too. `user_has_cap` intersects with the scope as a second layer, so a scope never grants what the account lacks. The denylist (`manage_options`, `edit_users`, `promote_users`, `create_users`, `delete_users`, `unfiltered_html`, `unfiltered_upload`, plugin, theme and core updates, `manage_network_*`) is applied to the `bloclabs_ssi_agent_scopes` filter's result as well. | `ScopeEnforcement`, `Scope::DENIED` |
| A5 | Completing an agent attempt through the browser route, or a browser attempt through the agent route. | `kind` on the attempt; each route family refuses the other's attempts with 404. | `BrowserController`, agent controllers, `TokenIssuer` |
| A6 | Issuing two tokens for one attestation, or a token for a consumed attempt. | Compare-and-set consumption and the token insert in the same request; `consumed` is terminal (threat 5). A later `POST /agent/token` answers 409 `already used`. | `AttemptRepository::transition()`, `TokenIssuer` |
| A7 | Guessing an attempt to poll or complete another agent's login. | 128-bit `public_id` plus the 256-bit attempt secret, carried in the `X-Bloclabs-Ssi-Attempt` header and stored as a hash; unknown and foreign attempts both answer 404 (threat 2). | `HeaderBinding` |
| A8 | Guessing a token. | 256 bits of entropy and one indexed lookup by hash. A refused token answers 401, never falls back to a cookie or to anonymous, and fires `bloclabs_ssi_agent_token_refused` with the reason and the hash, for lockout plugins. | `AgentToken`, `BearerAuthentication` |
| A9 | Bots registering accounts. | The agent route never provisions, whatever `linking_policy` says: the agent's own key must be linked to an account already, or `acts_for` must name a linked account that opted in. | `UserResolver::resolve_agent()` |
| A10 | The principal's account changes after issuance (role lowered, spam-flagged or locked out, user deleted, credential unlinked, password reset). | Capabilities are read from the account on every request, so a demotion reaches the agent at once; `wp_authenticate_user` and `authenticate` run on every token request; a missing user refuses. Deletion, removal from the site, unlinking the identity the token resolved through and a password reset revoke the token. | `BearerAuthentication`, `ScopeEnforcement`, revocation hooks |
| A11 | A credential revoked at the issuer after the token was issued. | Not detected until the token expires; the lifetime is the bound. Residual. | `agent_token_ttl`, `IssuedToken` |
| A12 | Personal data on chain, in the database or in logs. | On chain: commitments only, with the agent's own key as the committed subject; the principal is not on chain (ADR 0007 §5). In the database: the agent's subject as an HMAC under the subject key, a label from the credential's `agent.name` and `operator` or a keyed fingerprint, no addresses. In logs: nothing about the credential; the token itself appears nowhere once returned. | Contract, `IssuedToken::to_row()`, `AgentCredential::label()` |
| A13 | A REST route that checks only `is_user_logged_in()` is reachable with any scope. | Core routes check capabilities. A site with such routes keeps agent login off, or guards them itself: `BearerAuthentication::current()` returns the token that authenticated the request, so a route can tell a token from a session. Residual. | Deployment |
| A14 | Flooding `/agent/initiate` from headless clients. | The same per-client and site-wide caps as `/initiate`, counted in the same window (threat 11). | `InitiateController` caps |

## Residual risks

- Threat 1 is reduced, not removed, wherever the QR code is still what the holder uses: browsers without the
  Digital Credentials API, wallets that do not answer through it, and sites whose bridge does not offer it. Treat
  cross-device credential login like any QR login: keep the TTL short and the wallet's display of the verifier
  identity meaningful.
- The bridge holds the verifier's request-signing keys and the chain signing key. It is the most sensitive component;
  run it with the least network exposure that wallets allow.
- Without `BLOCLABS_SSI_SUBJECT_KEY` in wp-config.php, the subject key lives in the same database as the identities
  table, so someone holding a full dump can test guessed DIDs against it. Set the constant.
- The site-wide cap trades availability for the verifier's protection: a flood from enough addresses makes
  credential login answer 429 for everyone until the window passes. Password login is unaffected; raise
  `max_pending_total` for a large site.
- Revocation checks live in the verifier (walt.id `credential-status`), and issuer signatures are checked there
  against keys the verifier resolves from the issuer identifier; the registry governs which issuers are trusted, not
  whether a credential is really theirs ([ADR 0006](adr/0006-trusted-issuer-registry.md)). Until
  `FIREFLY_REGISTRY_API` is set, issuer trust is the walt.id `allowed-issuer` policy in the bridge configuration,
  which nothing records.
- Withdrawing an issuer's trust in the registry stops new logins with it. It ends no session already issued and
  unlinks no account; the `identities` table keeps the issuer, so an operator can find and unlink them.
- An agent token outlives a credential revoked at its issuer, for at most `agent_token_ttl` (A11), and a REST route
  that only asks whether someone is logged in is open to any scope (A13). A site with such routes keeps agent login
  off. Prompt injection against an agent (A2) is the agent's to defend; the reference client's rule, present only to
  the request your own initiate returned, is the one every agent must keep.
- The delegation an `acts_for` claim expresses is as trustworthy as its issuer (A3). The registry decides which
  issuers may say it; a site that lets a third-party issuer delegate its accounts has trusted that issuer with them.
